The brief

Built to an advertisement.

A logistics business looking for one developer to own a whole codebase named its stack precisely: .NET 9 minimal APIs with Dapper, comfortable writing raw SQL rather than leaning on an ORM, Next.js and TypeScript in front, Azure underneath. Rather than tell them I could, I built this, in the open, and wrote down what I decided and why.

.NET 9 minimal APIs with Dapper
Seven endpoints across consignments and the dashboard in api/: paged listing, one-round-trip detail via QueryMultiple, transactional booking, guarded status events, SAS-ticketed POD uploads, aggregate summaries. No ORM anywhere in the solution.
Comfortable writing raw SQL
328 lines of T-SQL: hand-written migrations, an effective-dated rate card model, a set-based demo data generator, CTEs, window functions, PERCENTILE_CONT, a filtered index for the overdue sweep. Every statement is parsed by SQL Server's own parser in CI, because no ORM also means no ORM safety net.
Next.js / React / TypeScript
An App Router dashboard in web/, server components fetching from the API, strict TypeScript with noUncheckedIndexedAccess, and an honest demo mode that badges itself when no API is configured.
Azure: App Service, Functions, SQL, Blob Storage
One Bicep file in infra/ standing up all four plus Application Insights, and a timer-triggered isolated-worker Function in functions/ that sweeps for consignments past their delivery window every fifteen minutes.
One developer owning the whole codebase
The repository is arranged for exactly that: migrations a person can read in order, SQL beside the handler that runs it, decisions written down in the README, CI that fails loudly, and nothing clever enough to need its author present.
Logistics and transport sector
The domain is real road freight: chargeable weight at the standard 250 kg/m³ cubic conversion, fuel levies, GST, depot lanes from Kewdale to Kalgoorlie and Port Hedland. Eleven years as an analyst in mining and heavy industry is where that fluency comes from.

The SQL, in the open

Nothing hides behind an ORM.

The queries a product like this lives on are exactly the ones ORMs generate badly and hide while doing it. Here every statement is a constant beside the handler that runs it, or a numbered migration a person can read in order. Two of them, as they appear in the code:

DashboardSql.LaneStats · api/Linehaul.Api/Data/DashboardSql.csT-SQL
WITH legs AS (
    SELECT o.Code AS OriginCode, d.Code AS DestinationCode,
           DATEDIFF(MINUTE, pu.OccurredAtUtc, del.OccurredAtUtc) / 60.0 AS TransitHours
    FROM dbo.Consignment AS c
    JOIN dbo.Depot AS o ON o.Id = c.OriginDepotId
    JOIN dbo.Depot AS d ON d.Id = c.DestinationDepotId
    JOIN dbo.ConsignmentEvent AS pu
        ON pu.ConsignmentId = c.Id AND pu.Status = @PickedUp
    JOIN dbo.ConsignmentEvent AS del
        ON del.ConsignmentId = c.Id AND del.Status = @Delivered
    WHERE c.Status = @Delivered
),
ranked AS (
    SELECT OriginCode, DestinationCode, TransitHours,
           PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY TransitHours)
               OVER (PARTITION BY OriginCode, DestinationCode) AS P90
    FROM legs
)
SELECT OriginCode, DestinationCode,
       COUNT(*) AS DeliveredCount,
       CAST(AVG(TransitHours) AS decimal(8, 1)) AS AvgTransitHours,
       CAST(MAX(P90) AS decimal(8, 1)) AS P90TransitHours
FROM ranked
GROUP BY OriginCode, DestinationCode
ORDER BY DeliveredCount DESC, OriginCode, DestinationCode;

Transit times per lane, measured from the event log rather than trusted from a column, with a p90 because averages are where bad runs go to be forgiven.

ConsignmentSql.TransitionStatus · the concurrency controlT-SQL
UPDATE dbo.Consignment
SET Status = @NewStatus, UpdatedAtUtc = SYSUTCDATETIME()
WHERE Id = @Id AND Status = @ExpectedStatus;

A compare-and-swap. The state machine in C# refuses illegal transitions first; then this predicate makes the write atomic, so two operators racing each other produce one clean 409 instead of a corrupt record. Zero rows affected means somebody else moved it, and the API says so.

  • The SQL is tested the way an ORM never needs

    The suite feeds every migration script and all thirteen embedded queries through Microsoft.SqlServer.TransactSql.ScriptDom, the parser SQL Server's own tooling uses: 18 parse checks. A typo in a query fails CI, not a customer request.

  • Dynamic filtering without dynamic danger

    The listing's WHERE clause is composed from a fixed whitelist of predicates; user input only ever travels as parameters, with LIKE wildcards escaped. There is a test that feeds it a SQL injection and shows the hostile text never reaches the statement.

  • Money behaves like an audit is coming

    Rate cards are effective-dated and never updated in place, charges are computed once at booking and stored, and the freight, levy and GST components reconcile by construction. There is a test that says so.

  • Files never pass through the API

    A proof-of-delivery photo gets a fifteen-minute SAS URL and goes straight from the driver's phone to Blob Storage. The API records metadata only, so the App Service stays small and stateless.

Verified

Checked, and said plainly.

The main page of this site argues that an AI coding agent is a delivery team that needs a specification and an adversary. This build worked that way, and the same standard applies to the claims on this page: here is what was actually verified, and what was not.

  • The solution compiles with zero warnings. Warnings are errors in every project file, so it stays that way.
  • All 52 tests pass: the rating arithmetic to the cent, every legal and illegal status transition, the filter builder against hostile input, and the full T-SQL parse of every query and migration in the repository.
  • The front end builds under strict TypeScript, including noUncheckedIndexedAccess, which is the flag most codebases turn off first.
  • The screenshots are real renders of the running application, taken in a browser, and the first set was thrown away: the demo generator marked old consignments as still moving, which made the overdue count read like a crisis. The generator now ages statuses the way a live board would. Looking at the rendered thing catches what reading the code does not.
  • Not done, and not claimed: this repository has not been deployed to a live Azure subscription and has not been load tested. The Bicep describes the intended topology and is written to be deployed; nobody should read "deployed and humming" into a repo that does not show it.
