Six tools, live since 19 August 2026

Rain Check

Answers whether an Australian field-service job can be worked at a place on a day, for a given trade, from live forecast, daylight and public holiday data. Built for the shape of problem a trades business actually has: not "what is the weather", but "can we book the Thursday concrete pour in Bendigo".

The judgement is deliberately visible. Every threshold that produced a verdict comes back in the response and can be overridden per call, so nothing is hidden from the model. An ambiguous suburb comes back as a question with candidates rather than a guess. A date past the sixteen-day forecast comes back labelled as having no data, and the tool tells the model in as many words not to substitute an opinion about the weather.

  • 01

    Every local test passed, and every deployed call returned 500

    I wrote the transport layer against the Web Request object. It typechecked, and the tests passed, because the tests built their own Request objects. The platform hands the handler a Node IncomingMessage. The fix to the code was small. The useful fix was to the test, which now stands up a real HTTP server and talks to it over a socket: a test that builds its own request shape only ever tests that shape.

  • 02

    A silently ignored parameter, surfacing as a confident wrong answer

    The geocoder takes countryCode, not country. The wrong name is accepted without complaint and ignored, so a search for Richmond returned Virginia, British Columbia and California, my Australia filter discarded every row, and the server told the caller that no such place existed. Fixed the parameter, widened the page size (the upstream ranks globally by population, so a small page for a name shared with a large overseas city contains no Australian rows at all), and filtered to populated-place codes so Richmond Oval stops presenting itself as a suburb.

  • 03

    A stateless server hanging on a request it should have refused

    A GET on the MCP endpoint opens the server-to-client notification stream. Stateless, there is no session and nothing to push, so the transport returned an SSE body that never closed and the function ran to its timeout. GET and DELETE now answer 405 with the reason. The test asserts a prompt refusal rather than a status code, so a regression shows up as a hang instead of a silent pass.

Two calls I made rather than bugs I fixed. The obvious public holiday dataset on data.gov.au is officially inactive and still serving plausible dates, so anything built on it keeps working and quietly goes stale. I moved off it and made the limitation part of every response rather than a footnote, with the official state page returned alongside the data. And the Bureau of Meteorology's API is the source an Australian tool should want, but its own terms say you must not use, copy or share it, so the server runs on Open-Meteo under CC BY 4.0 instead.

Doorknock

Researches a company from its own domain, judges it against a lead profile the caller supplies, and writes the result into HubSpot. It reads the company's own home page and its public DNS: the marketing and CRM tools loaded on the page, which pages exist, who handles their email, and whether their outbound email is protected. Nothing is bought from a data provider, and nothing is inferred about revenue, headcount or ownership.

It is the go-to-market shape of the same discipline: enrichment, qualification and routing, with the reasoning attached to every rule instead of a score nobody can interrogate.

  • 01

    The credential never touches the model

    The obvious design is a token parameter on the HubSpot tools, and it is the wrong one: a tool parameter is produced by the model, which puts the secret in the prompt, the context window, the client's transcript and any log that records tool calls, and makes it something a model can be talked into sending elsewhere. The token travels on the HTTP request instead, and no tool schema has a field for it. One of the adversarial checks exists purely to assert that none ever grows one.

  • 02

    A refusal wrapped in a success

    Found by the adversarial suite on its first run against the deployment. Asking the server about 169.254.169.254, the cloud metadata address, returned HTTP 200 with a result object. Nothing leaked, because the fetch guard refused to contact it. But a research call runs the page fetch and the DNS lookups in parallel and the DNS half carried on, so the caller got a 200 wrapped around a refusal. Defence in depth had worked and the response contract had not. The address rules now run at the front door. In the same run: redirects were being followed by the runtime, which validates nothing, so a public host answering 302 to an internal address would have gone straight through the guard. Hops are now followed by hand and each one re-checked.

  • 03

    A test that failed on something it never looked at

    The adversarial script truncated every response body to 600 characters before checking it. One assertion looked for a field about four kilobytes into the response, never saw it, and reported the server broken when the server was correct. That cost more time than any of the real defects. A test that decides a pass or a fail from something it never actually read is worse than no test, because it is believed.

  • 04

    Only an independent check could have found this one

    Equal-priority MX records came back in a different order on every call, because resolvers rotate them and sorting by priority alone is not a total order. It was caught by the script that re-fetches every fact from a different resolver than the server used and compares field by field. Every one of my own tests compared the server against itself, and none of them could have seen it.

03

Adversarial review of a system built by agents

Two full security and correctness reviews of a live video shopping platform, the second one reviewing the remediation of the first. Every finding below was driven by hand against the running application, not read off a diff.

2026, anonymised, no repository linked

Six exploits driven, and what the second pass found

The scorecard from re-driving the six original exploits after remediation: three genuinely fixed at the root cause, one still open, one reopened, one re-broken by its own fix. The worst holes were shut. The habits that produced them were not.

  • 01

    The new sign-in was bypassed by its own sibling

    A one-time-code sign-in had been added and guarded one route. The older route still minted an identical session for any email address, on a looser throttle, never consulting the code system at all. I drove it: signed in as a retailer with a live show and ended their broadcast. The same handler also failed open, dropping the code requirement entirely on any database error.

  • 02

    Erasure cascade-deleted paid invoices while promising it had not

    The account erasure path deleted the account row, and the invoices foreign key cascaded. The response told the user their financial records were retained. Two failures in one: financial records destroyed, and a statement to the user that was not true.

  • 03

    A proof page that reported a guaranteed pass

    A page existed to prove cache behaviour, and it read two response headers cross-origin. The CORS policy exposed neither, so every read came back null, the miss count was structurally zero, and the page reported one hundred per cent, always. The project's own review document had recorded it as verified. The same missing header also made a separate caching fix inert.

  • 04

    One reported finding I checked and rejected

    An agent reported that stream keys leaked through one of the read paths. I traced it: that path uses a serialiser which redacts the key to a boolean. Not a finding, and I said so. A review that accepts everything it is handed is not a review, and the same rule applies whether the source is a person or a model.

The earlier design pass on the same platform found four commercial defects by reading the code against the pricing model, each verified by hand: any signed-in account could self-select the top plan and take its allowance free, because only one tier was staff gated; no plan at all meant no cap, because zero was the "never block" sentinel; overage was unreachable code, because the hard caps and the included allowances were the same numbers, so the plans could not bill a cent above the allowance; and the summary used by the dashboard counted buy-link clicks as orders and buyers, because it was missing a filter its sibling function had.

04

Rules, eligibility and decisions at scale

The through-line from the analysis work to the agent work. An agent that decides something has the same problem a statutory scheme has: the logic must be inspectable, the evidence must travel with the decision, and "we could not tell" must not be recorded as "no".

National Redress Scheme

Led requirements analysis for the scheme at Services Australia, including the design of a rules engine to determine eligibility for redress: translating legislation and policy into functional requirements and eligibility logic for implementation in enterprise and customer relationship platforms. The rules had to be readable by the people accountable for them, not buried in code.

Veteran Centric Reform

Led the Qualifying Service work package: business analysis, solution specification and stakeholder collaboration across a large programme with multiple delivery teams.

Electricity distribution ring-fencing

Nine months at Essential Energy on the programme separating the regulated distribution network for regional and rural New South Wales from its contestable services company, under the Australian Energy Regulator's ring-fencing guideline. Four workstreams, all mine: information separation, process and ways of working, compliance and reporting, and systems and integration change. Regulatory obligations traced into operating controls and into the evidence supporting compliance reporting to the regulator.

Where it lands in the agent work

Doorknock's qualification rules arrive with the call and come back with the answer, so changing who counts as a good lead never needs a deployment and the logic that produced a verdict is visible to whoever reads it. A rule naming a signal that does not exist is reported as an unknown signal rather than silently counted as a miss. A signal that could not be determined blocks the tier instead of failing it, because a lead nobody could assess is not the same as a bad lead. That is the redress rules engine lesson, applied to a sales pipeline.

06

How I work

Three rules, each one visible in something above rather than asserted here.

A failure is a turn, not a crash

Every error in both servers comes back as content with a next step the model can act on, so an ambiguous suburb becomes a clarifying question and a company name given instead of a domain becomes a request for the web address. Neither will guess. The single most confident-sounding wrong answer this class of tool gives is a domain inferred from a company name, and both of them refuse to do it.

Absence is reported as absence

A tag can load through a tag manager, sit behind a consent banner, or live on an inner page. So the answer says "not detected on the home page", never "they do not use HubSpot", and all fifty-four signals in the vocabulary carry a sentence about what their absence does not prove. The same instinct is why nothing on this page is illustrated with invented data.

My own tests passing proves very little

Both servers ship a script whose only job is to check them against sources that have nothing to do with the repository: a different DNS resolver than the server used, the company's own page fetched directly, the upstream API's own numbers. It has found things no test of mine could have, because every test I write compares the server against itself. There are no mocks in any suite, in either project.

Everything on this page is either a system you can connect to, a repository you can read, or work described generically because it belongs to a client. Where something cannot be checked, the page says so on the spot rather than in a footnote.
